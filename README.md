# Drone Dynamics and Control Simulator

A Python quadrotor simulator for studying flight dynamics, PID control, and wind disturbances.

## Overview

The simulator models a droneâ€™s motion and uses feedback control to track a target position and heading. It combines altitude control with cascaded horizontal-position and orientation control, then mixes their outputs into four motor commands.

The simulation uses `controllerV1.py` and a waypoint route generated by `routeplanner.py`.

## Features

- Three-dimensional position, velocity, orientation, and angular-state simulation.
- Motor thrust, gravity, and roll, pitch, and yaw torque calculations.
- PID control of altitude, horizontal position, and orientation.
- Tilt compensation, motor-speed limits, and commanded tilt limits.
- Wind forces based on relative air velocity.
- Plots of altitude, vertical velocity, motor speeds, orientation, and horizontal position.

## Physics Model

### Coordinates and Assumptions

- Position: $\mathbf{p} = [x,y,z]^T$, with world $z$ pointing upward.
- Orientation: $\boldsymbol{\eta} = [\phi,\theta,\psi]^T$ for roll, pitch, and yaw.
- Thrust acts along the positive body $z$ axis.
- All quantities use SI units; internal angles are in radians and motor speeds are in rad/s.
- The rotational model includes gyroscopic coupling between axes. Body angular velocities update a normalized quaternion, which is converted back to Euler angles for recording and control.

### Core Equations

| Calculation | Formula |
| --- | --- |
| Motor thrust and limit | $T_i = \min(k_T\omega_i^2, T_{\max})$ |
| Level hover speed | $\omega_{\mathrm{hover}} = \sqrt{mg/(4k_T)}$ |
| Maximum motor speed | $\omega_{\max} = \sqrt{T_{\max}/k_T}$ |
| Body-to-world rotation | $R = R_z(\psi) R_y(\theta) R_x(\phi)$ |
| Wind force | $`\mathbf{F}_{\mathrm{wind}} = c_w(\mathbf{v}_{\mathrm{wind}} - \mathbf{v})`$ |
| Translational dynamics | $m\ddot{\mathbf{p}} = R[0,0,\sum_i T_i]^T + [0,0,-mg]^T + \mathbf{F}_{\mathrm{wind}}$ |
| Roll and pitch torque | $\tau_\phi = L(T_2 - T_4),\quad \tau_\theta = L(T_3 - T_1)$ |
| Yaw torque with thrust limiting | $\tau_\psi = (k_\tau/k_T)(T_1 - T_2 + T_3 - T_4)$ |
| Angular acceleration with gyroscopic coupling | $`\dot{\boldsymbol{\omega}} = I^{-1}\left(\boldsymbol{\tau} - \boldsymbol{\omega}\times(I\boldsymbol{\omega})\right)`$ |
| Velocity-first integration | $`\mathbf{v}_{k+1} = \mathbf{v}_{k} + \mathbf{a}_{k}\Delta t,\quad \mathbf{p}_{k+1} = \mathbf{p}_{k} + \mathbf{v}_{k+1}\Delta t`$ |

Here, $m$, $g$, $L$, and $I_j$ represent mass, gravitational acceleration magnitude, arm length, and axis inertia. The coefficients $k_T$, $k_\tau$, and $c_w$ describe motor thrust, yaw torque, and wind force.

For rotational dynamics, $I = \mathrm{diag}(I_\phi,I_\theta,I_\psi)$ is the inertia matrix, $\boldsymbol{\omega}$ is angular velocity, and $\boldsymbol{\tau}$ is net torque. The cross-product term accounts for gyroscopic coupling. Angular velocity uses velocity-first integration; orientation applies the resulting body-frame rotation through a quaternion. Flat ground contact clamps altitude to ground height and prevents downward velocity at contact. This is a simple non-bouncing contact model, without landing-gear or friction dynamics.

## Control System

### Controller Loops

The horizontal-position and orientation controllers form a cascade:

- **Position loop:** computes world-frame horizontal commands, rotates them by the current heading, and converts them into desired pitch and roll angles. Each error contributes once per integration step.
- **Orientation loop:** tracks the desired roll, pitch, and yaw using motor-speed corrections.
- **Altitude loop:** independently adjusts the common motor speed to track the height target.

Tilt compensation increases the base motor speed during tilted flight. Motor mixing combines this base speed with the orientation corrections. All controllers update at each simulation step.

### Control Equations

For each controlled state, $e_j = r_j - y_j$ is the tracking error and $S_j = \sum e_j\Delta t$ is the accumulated error.

| Controller component | Formula |
| --- | --- |
| Altitude PID | $u_{z,k} = K_{P,z}e_{z,k} + K_{I,z}S_{z,k} - K_{D,z}v_z$ |
| Altitude motor command | $\omega_b = \mathrm{clip}(\omega_{\mathrm{hover}} + u_z, 0, \omega_{\max})$ |
| Horizontal position to pitch | $\theta_d = \mathrm{clip}(K_{P,x}e_x + K_{I,x}S_x - K_{D,x}v_x, -\theta_{\max}, \theta_{\max})$ |
| Horizontal position to roll | $\phi_d = \mathrm{clip}(-(K_{P,y}e_y + K_{I,y}S_y - K_{D,y}v_y), -\phi_{\max}, \phi_{\max})$ |
| Orientation correction | $`c_{j} = \mathrm{clip}(K_{P,j}e_{j} + K_{I,j}S_{j} - K_{D,j}\dot{\eta}_{j}, -c_{\max}, c_{\max})`$ |
| Tilt compensation | $\omega_c = \mathrm{clip}(\omega_b/\sqrt{\max(\cos\phi\cos\theta, 0.5)}, 0, \omega_{\max})$ |

Clipping limits a value between the specified bounds. The altitude and position loops use measured velocity for derivative damping. The orientation loop transforms body angular rates into Euler angle rates, wraps yaw error to the shortest turn, and freezes integral changes that worsen correction or motor saturation. The horizontal formulas above describe heading zero; at other headings the world commands are rotated into the heading frame.

### Motor Mixing

The compensated base speed and orientation corrections produce four motor commands:

$$
\begin{aligned}
  \omega_1 &= \omega_c - c_\theta + c_\psi \\
  \omega_2 &= \omega_c + c_\phi - c_\psi \\
  \omega_3 &= \omega_c + c_\theta + c_\psi \\
  \omega_4 &= \omega_c - c_\phi - c_\psi
\end{aligned}
$$

Each command is then clipped to $[0,\omega_{\max}]$.

## Usage

### Run the Simulation

With `drone-sim` active, run this command from the project directory:

```bash
python main.py
```

The simulation prints the final drone state and opens plots of altitude, vertical velocity, motor speeds, orientation, and horizontal position.

### Configure a Run

Edit flight and physical terrain settings near the top of `main.py`. Graph scale settings are in `plotting.py`:

| Setting | Parameters |
| --- | --- |

| Target position and heading | `TARGET_X`, `TARGET_Y`, `TARGET_HEIGHT`, `TARGET_YAW` |
| Altitude gains | `KP`, `KI`, `KD` |
| Orientation gains | `ROLL_GAINS`, `PITCH_GAINS`, `YAW_GAINS` |
| Position gains | `X_POSITION_GAINS`, `Y_POSITION_GAINS` |
| Controller limits | `MAX_TILT_DEGREES`, `MAX_ORIENTATION_CORRECTION` |

| Simulation timing | `DT`, `SIMULATION_TIME` |

### Landing and Automated Checks

Landing is enabled with `INCLUDE_LANDING = True` in `main.py`. The default `TERRAIN_MODE = "landscape"` creates a reproducible 28 × 28 m view of rolling hills, a ridge, valleys, and smaller undulations. Set `TERRAIN_SEED` to vary the smaller undulations; the major landforms are defined in `LandscapeTerrain.features` in `terrain.py`. This is a synthetic landscape, not surveyed terrain. Rendering adds directional sunlight and elevation colors.

The modes `"flat"`, `"hill"`, and `"slope"` remain available; configure the hill center, height, and width or `TERRAIN_SLOPE` in `main.py`. Planning, physics, landing, and plotting all use the same terrain model. Ground elevation is queried at the drone's actual horizontal position. The landscape planner samples the route and adds a conservative gradient-based allowance for peaks between samples.

The route climbs above the highest terrain along the straight crossing before moving horizontally. At the destination, the landing controller aligns over the target, descends at `LANDING_DESCENT_SPEED`, and slows to `LANDING_FLARE_SPEED` below `LANDING_FLARE_HEIGHT`. Descent pauses if position, horizontal speed, or tilt moves outside the alignment limits. A 3 cm contact bias ensures touchdown. Low-speed contact disarms the motors and completes the mission; an impact above 0.35 m/s is recorded as `hard_landing` and does not complete the mission successfully.

The landing site and footprint are checked against `MAX_LANDING_SLOPE_DEGREES` (20 degrees by default). Steeper destinations raise a clear error before flight. This simulator uses point contact with a terrain normal; it does not model landing gear, tipping, or surface friction. Increase `SIMULATION_TIME` for longer routes.

For example, to land on the isolated hilltop:

```python
from main import run_simulation
from terrain import HillTerrain
state, data = run_simulation(goal_position=[5.0, 4.0, 2.0],
                             terrain=HillTerrain(), include_landing=True, duration=70.0)
```

The approach altitude is raised to clear the hill, and touchdown uses its local elevation near 3 m. Recorded data includes `clearance`, `ground_height_history`, `landing_phase`, `landing_failed`, and `touchdown_speed`.

Run regression checks without saving plots:

```bash
python -m unittest -v
```

For pip-based environments, install dependencies with `python -m pip install -r requirements.txt`.

### Tune PID Gains (Optional)

For a broader search that applies the best validated gains automatically, run:

```bash
python retune_pid.py
```

This searches two random seeds with 120 trials per controller per seed, compares candidates with the starting gains, and checks flight at 90-degree yaw and landing before applying gains. It writes `pid_retuning_report.json`, `optimized_pid_gains.json`, and updated plots. The selected gains are the best tested under the recorded model, bounds, and scoring criteria; the search does not prove a global optimum.

If the selected gains approach the search limits, `python retune_pid.py --expanded` performs another search with wider ranges. It preserves the prior report as `pid_retuning_report_initial.json` and compares new candidates with the currently configured gains.

Run the tuning tool separately:

```bash
python auto_tune_pid.py
```

Use `auto_tune_PID.py` if that is your repositoryâ€™s filename. The tool reads the current gains and flight settings from `main.py`, and uses the same control step and environment as the main simulation. It compares candidates against the current gains in both a combined X/Y trial and the actual configured waypoint mission. Candidates must complete the mission and score no worse in either comparison; otherwise the output retains the current gains. The tool writes `optimized_pid_gains.json` (including validation results) and `auto_tune_results.png`. Copy accepted gains into `main.py`, then rerun the simulation.

## Continuous path tracking

The mission follows a moving position and velocity reference along the existing
terrain-clearance route. Collinear cruise waypoints are passed without stopping.
The drone finishes its vertical climb before crossing horizontally and slows to
rest at the destination before the existing landing controller takes over.

Adjust `MAX_FLIGHT_SPEED` (1.2 m/s), `MAX_FLIGHT_ACCELERATION` (0.8 m/s�),
`MAX_CLIMB_RATE` (0.8 m/s), `MAX_DESCENT_RATE` (0.4 m/s), and
`PATH_LOOKAHEAD_DISTANCE` (1.0 m) in `main.py`. These limits apply to the flight
reference; the actual drone can deviate under wind and controller tracking error.
Look-ahead throttling slows the reference when the drone falls behind. The
look-ahead distance is a slowing threshold rather than a strict distance bound.
Landing continues to use its separate descent and flare settings.


Roll and pitch commands use a first-order filter followed by a per-axis rate
limit before reaching the attitude PID. Configure TILT_SMOOTHING_TIME (0.03 s)
and MAX_TILT_RATE_DEGREES (10 degrees/s) in main.py. The filter starts from
the measured tilt and preserves the existing maximum tilt limit. Yaw commands
are unchanged. These settings limit commanded tilt, not actual angular motion;
extra filtering adds response delay, so check braking and landing when adjusting
them. Fresh controllers start with fresh filter state for each simulation.


Flight sections now use a fifth-degree S-curve with zero speed and acceleration
at each section endpoint. MAX_FLIGHT_JERK (1.0 m/s^3) controls how quickly
reference acceleration may change. Section duration is calculated from the
speed, acceleration, climb/descent, and jerk limits. Collinear waypoints remain
continuous; the existing climb/cross corner still finishes at rest. The smooth
look-ahead clock also reserves acceleration and jerk for slowing when tracking
falls behind. Its distance threshold remains soft: jerk-limited stopping needs
extra distance. This flight profile does not change the separate landing flare.
